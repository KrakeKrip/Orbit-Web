## 1. Pure contracts / модель
Task title: trim, 1–500 Unicode code points (PG char_length, не UTF-16). Дубликаты разрешены. Reject wrong type/null/empty, NUL и unpaired surrogate (некорректный Unicode не должен доходить до PostgreSQL и превращаться в 500). UI не обрезает допустимое имя native UTF-16 maxlength. Markup отображается только текстом.
POST принимает ровно `{title:string}`. Сервер/DB генерирует UUID, owner из session; project_id/parent_id/notes/planned_date/planned_time/deadline_date/recurrence_rule/completed_at/deleted_at=NULL, priority=4, sort_order=0, revision=0. Не создавать фиктивные данные/проект/даты.
PATCH принимает непустой subset `{title?:string,completed?:boolean}`, unknown fields/null/array/types запрещены. Совместный title/completed атомарен. id/owner/project/parent/notes/priority/dates/recurrence/order/created_at нельзя менять через этот контракт. Они остаются неизменными и в seeded существующих rows.
DTO текущего subset: `{id,title,projectId:string|null,parentId:string|null,completedAt:ISO|null,revision:number,createdAt:ISO,updatedAt:ISO}`. Owner/секреты не возвращать. Прочие task fields пока вне write API; не перезаписывать их defaults на update.
UUID syntax валидируется до service. Ошибки без raw input/SQL/stack. Pure validation отдельно от transport и persistence.

## 2. Service / ownership / Inbox
Actor только из requireUser; page requireUserOrRedirect. Все list/read/update/delete и completion journal queries owner-scoped. Item mutation WHERE id AND owner_id, никакого unscoped update после read. Foreign/unknown/deleted UUID → одинаковый 404 NOT_FOUND для GET/PATCH, без утечки данных. Client owner/project/parent spoofing запрещён как unknown payload/query, не источник actor.
Collection — Inbox: только own non-deleted root tasks (parent_id=NULL) с planned_date=NULL; project_id=NULL либо own project archived_at=NULL. Root task в активном проекте без даты относится к Inbox согласно PRODUCT, хотя назначение проекта пока не поддерживается. Исключать архивные проекты на сервере, не через UI фильтр; отсутствие связи не должно приводить к меж-owner join. status=open|completed|all, default open; completed фильтруется completed_at. sort_order ASC, created_at ASC, id ASC, без manual reorder/priority sorting. Ошибка БД не превращается в пустой список; нет меж-user cache.
GET item: свой non-deleted task, в том числе с датой/в архиве; не отдавать foreign/deleted rows. Root one-off mutations допустимы; child (parent_id!=NULL) или recurrence_rule!=NULL →409 UNSUPPORTED_TASK без изменений/журнала (эти операции будут спроектированы в TASK-009/011). Собственная задача архивного проекта при mutation →409 PROJECT_ARCHIVED без записи. Проверки task/project state выполняются в transaction; project ownership проверить даже при наличии composite FK. Если project имеется, согласовать archive check с конкурентным archive через row lock проекта (shared lock либо другой доказанный механизм): архив не может вклиниться между проверкой и записью. Не менять project service/schema без согласования; установленный archive UPDATE должен сериализоваться с project row lock.

## 3. One-off completion / reopen / soft delete
PATCH под transaction + owner-scoped task row lock (или эквивалентная доказанная атомарность), обновление title/completed не теряет unrelated writes. Revision увеличивается на 1 только при реальном изменении task state (включая title/complete/reopen/delete); updated_at server time только при изменении. Полный no-op возвращает текущий DTO, не меняет revision/timestamps. Конкурентная запись одного поля — last serialized write wins; expectedRevision/ETag для этого one-off subset пока не требуется.
completed=true из open: один server timestamp становится task.completed_at и task_completions.completed_at; вставить journal row в той же transaction, owner/task проверены, occurrence_date=NULL, completed_revision — task revision ДО перехода, idempotency_key — server-generated UUID. Вставка journal и изменение task/revision атомарны. Повтор completed=true для already completed — без нового log/revision/timestamp (независимо от разных запросов). Два одновременных complete одного open task → ровно один переход и log, оба возвращают completed DTO. Отказ journal INSERT откатывает и изменение задачи.
completed=false из completed: completed_at=NULL, revision+1; прежняя completion history не удаляется. Повтор reopen — no-op. Следующее complete после reopen добавляет новый log с новой completed_revision, не сталкивается с unique(task_id,completed_revision). Изменение title одновременно с completion также одна revision на итоговый PATCH, одна transaction/log. Завершение родителя не завершает детей.
DELETE — soft delete, никогда физический DELETE. Root task: deleted_at server timestamp, revision+1/updated_at; в одной transaction скрыть также собственные ещё не удалённые direct children (parent_id=root.id), не менять project/completion log/completed_at/dates. Это сохраняет PRODUCT-инвариант удаления родителя; child creation/move/UI остаются TASK-009. Уже deleted children сохраняют свои deleted_at/revision. У всех новых удалённых rows один timestamp. Нельзя изменять rows другого owner. Повтор DELETE своего уже удалённого root →204 no-op, без изменения timestamp/revision; foreign/unknown →404. GET/PATCH deleted →404; deleted не попадают ни в один status list. Восстановление/undo не реализовывать.
Порядок блокировок и transaction boundaries объяснить в отчёте; не полагаться на двойной клик guard для целостности server.

## 4. HTTP API
- GET /api/v1/tasks?status=open|completed|all →200 `{tasks:TaskDTO[]}`. Это Inbox collection; единственный query status, duplicate/unknown key/value →400. Никакого owner/project/date/parent filter в этом TASK.
- POST /api/v1/tasks JSON `{title}` →201 `{task:TaskDTO}`; query не поддерживается →400.
- GET /api/v1/tasks/[taskId] →200 `{task}`.
- PATCH item JSON subset title/completed →200 `{task}`.
- DELETE item без body →204; непустой body →400, query не поддерживается. UI требует подтверждение, API auth/Origin всё равно обязательны.
Item query/invalid UUID →400 VALIDATION_ERROR. Valid anonymous request →401 UNAUTHENTICATED; foreign/missing/deleted поведение выше; 409 UNSUPPORTED_TASK/PROJECT_ARCHIVED; unexpected →500 INTERNAL без приватных подробностей. Envelope `{error:{code,field?}}`.
POST/PATCH JSON exact application/json media type с parameters/регистром; другие415, malformed400, body>2KiB413 с потоковым лимитом (500 emoji title помещаются при стандартном JSON). DELETE без JSON media requirement, непустой body проверяется bounded reading, >2KiB413. Mutations требуют точный configured BETTER_AUTH_URL Origin, missing/null/foreign403; не доверять Host/Forwarded и Better Auth CSRF в собственных routes. Все success/errors (включая204) private,no-store; no wildcard CORS. Auth check каждого API, server-only business layer. Не дублировать правила в Server Actions.
